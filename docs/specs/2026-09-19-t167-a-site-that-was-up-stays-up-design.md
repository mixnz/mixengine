# T167 — A site that was up stays up

Roadmap task [T167](../roadmap/phase-21-a-site-that-stays-up.md), phase 21. 2026-09-19. Decision: [ADR 0041](../decisions/0041-mixengine-stops-nothing-a-person-did-not-ask-it-to.md).

**The case this comes from** is not a bug report. It is the sentence a person says before they
uninstall: *the site worked this morning, now it does not open.* Nobody using MixLab cares how
MixEngine saves memory; they see a site that was up and is not. MixLab's experience is the product,
and MixEngine's efficiency is worth exactly as much as it stays invisible.

Today two things produce that sentence on a default home, and neither is a malfunction — both are
the design working as written:

1. **Idle shutdown is on by default.** `php-fpm` stops after 30 minutes nobody used it, and MariaDB,
   MySQL, PostgreSQL, Redis, Memcached and MongoDB after 60 (`resource-isolation.md`, T70/T70a). The
   next request is meant to start them again (on-demand start), and a person who has never read that
   paragraph has no idea any of it is happening. When the wake works, the first request is slow; when
   it does not — a path the wake was never built for, a wake that fails — the site is simply down,
   and the Dashboard says **Stopped** in red about something nobody stopped.
2. **The front end does not come back with the daemon.** `service.create` leaves `autostart` off and
   nothing ever ticks it on a person's behalf (T116, T129). So after a reboot, after *Start MixEngine*,
   after `npm run dev:app` — any fresh daemon — nothing listens on port 80/443 and every site on the
   machine is dead until somebody finds Caddy on the Dashboard and starts it. The on-demand fallback
   cannot help: it lives inside the front end's own configuration. (Measured on this machine's
   `MixEngine-dev`: `caddy`, `php-fpm@8.4.24`, `mariadb@main`, `redis@main` all have `autostart = 0`.)

## Principle

**A site that was up stays up until a person stops it.** Saving resources is something a person
turns on, knowing what it does — never a default that makes a working site stop working. Where
MixEngine does stop something on its own, MixLab says so in words that describe what the person
will see (*resting, starts on the next visit*), not what the state machine is in.

## What is already true

- `services.idle_minutes` has three states: `NULL` (the recipe's default), `0` (never), `n`
  minutes (`generate.rs`, the `idle_after` match). The recipe defaults live in each recipe's
  `idle_default()` — `php_fpm.rs`, `mariadb.rs`, `mysql.rs`, `postgres.rs`, `redis.rs`,
  `memcached.rs`, `mongodb.rs`.
- The reaper is `mixengined::services::idle`; it already exempts a service something running depends
  on and the pools of a project marked `keep_warm` (`projects::kept_warm`).
- `keep_warm` is a column (`0008_project_keep_warm.sql`), a field on `ProjectSummary` /
  `ProjectUpdate`, the verb `mix project keep-warm`, and a checkbox in MixLab's project form
  (*Keep this project's services out of idle shutdown*).
- An idle stop is recorded: the transition carries `StateReason::Idle { after }`, and
  `services.stopped_by` says `daemon`. **`ServiceSummary` does not carry either**, so MixLab's
  Dashboard cannot tell an idle stop from a crash or from a person's Stop — it draws all three as
  `stopped`, tone `bad`.
- A front end already answers a dead upstream with a page of MixEngine's own instead of its raw
  error: `handle_errors 502 504` (Caddy) / `error_page 502 504 = @mixengine_welcome` (nginx), serving
  `generate/welcome.rs`'s page (T124).
- `[services]` in `config.toml` carries a comment that is now false (*"Nothing does it by itself
  yet"*).

## D1. Idle shutdown is off unless a person turns it on

- **Every recipe's `idle_default()` answers `None`.** A row at `NULL` — every row nobody touched —
  is then never idle-stopped. Rows a person set (`0` or `n`) keep exactly what they said.
- **One switch for the home, off by default**: the `settings` row `services.save_resources`
  (absent = off), read by the generator. **In SQLite and not in `config.toml`**: it is changed from a
  running window, and `config.toml` is read once at daemon start; the `settings` table already has
  `updates::records::{get,set}` for exactly this. The idle sweep rebuilds its graph from the rows on
  every pass (`registry.graph()`), so a change reaches the next sweep with nothing regenerated by
  hand. When it is on, a `NULL` row gets the recipe's *saving* default — the numbers that are
  defaults today (30 min for a pool, 60 for the rest) move from `idle_default()` to a new
  `idle_when_saving()` on the recipe, so the knowledge of "how long is sensible for this program"
  stays where it was.
- Reached from **MixLab Settings** as one toggle — *Save battery: pause services nobody is using*
  — with one sentence under it saying the next visit wakes them and may take a second. Reached
  from `mix` as `mix service save-resources [--on|--off]` (every mutating method reachable from the
  CLI — the non-negotiable rule), beside `mix service set-front-end`, the other home-wide switch
  about services. Two API methods, `service.save_resources` (read) and
  `service.set_save_resources` (write), in `mixengine_proto::rpc`'s method list.
- **An upgrade changes behaviour for homes that never chose**: a home on 0.0.6 with a `NULL` row
  was idle-stopping and will stop doing so. That is the point, and it goes in the CHANGELOG under
  *Updated*. A home whose owner set a number keeps idle-stopping.

**Why a home switch and not per-service defaults in the UI**: a person thinks "my laptop, battery"
and not "php-fpm, 30 minutes". Per-service `mix service idle` stays for the few who want it.

## D2. `keep_warm` goes away as a thing a person sees

With D1, a project's pools are only ever idle-stopped on a home that asked for it, and on that home
"keep this one warm" is still a meaningful exception — but not one worth a checkbox with the words
*idle shutdown* in it on every project form.

- **The checkbox leaves the project form**, and the *Keep warm* column leaves the Projects table.
- **The column, the API field and `mix project keep-warm` stay** — they are the wire and the CLI,
  and removing them is a breaking change for nothing: on a home that saves resources, the reaper
  still honours them.
- When `save_resources` is on, the Settings sentence says the one thing a person needs: a project
  can be kept running with `mix project keep-warm`. (A MixLab control for it can come back later,
  worded as *Always keep this project running*, if anyone asks.)

## D3. MixLab says "resting", not "stopped", when MixEngine stopped it

- **`ServiceSummary` gains `stopped_by: Option<StoppedBy>`** (`person` | `daemon` | `never`),
  optional on the wire per ADR 0019, `None` when running. Read from the column that already exists.
- **Dashboard and Services draw a daemon-stopped service as its own label and tone**: *Resting —
  starts on the next visit*, tone `busy`-grey rather than `bad`-red, and the row's switch still
  offers Start. A crash stays `failed`/red; a person's Stop stays `stopped`.
- `serviceStateLabel.ts` gets the one extra case, keyed off `(state, stopped_by)`; its test grows
  with it. Older daemons send no `stopped_by` and render exactly as today.

## D4. The front end comes back with the daemon

*(Accepted in review, 2026-09-19, with the one-time migration.)*

- **A front-end service (the recipe's role is `FrontEnd` — `caddy`, `nginx`) is created with
  `autostart = true` when nobody said otherwise.** `ServiceCreate.autostart` is already an
  `Option<bool>`; `api/create.rs` resolves `None` to the recipe role's default instead of `false`.
  An explicit `false` is still honoured. `blueprint.apply` passes `Some(true)` when asked for
  `--autostart` and `None` otherwise (it passes `Some(false)` today, which would override this).
- **A one-time migration** sets `autostart = 1` on existing rows whose package is `caddy` or
  `nginx`. A person who deliberately turned a front end's autostart off loses that once; the
  CHANGELOG says so under *Updated*. The migration names the two packages because a migration cannot
  consult the recipe catalogue — it is a fact about the rows as they are today, frozen with it.
- Why this is safe where T116/T129 refused it: those refused MixEngine starting *anything* on a
  person's behalf. The front end is the one service whose absence breaks every site at once and
  which costs a few MB; it is closer to part of the daemon than to a service somebody chose.
- Not the daemon's own login item (T85b) — starting MixEngine at login stays a person's choice in
  Settings.

## D5. When a wake fails, the page says so

With D1 a wake only happens on a home that asked for resource saving, but it still happens there.
The welcome page (T124) already catches `502 504`; it currently says *there is nothing behind this
site yet*, which is wrong when there is something behind it and it is starting or failed to start.

- The front end's error handler serves a **second page for a site that has a backend**: *This site
  is starting…*, which refreshes itself after two seconds, three times, and then says *MixEngine
  could not start what this site needs — open MixLab to see why.* No machine facts on it (T124's
  D5 holds: the page is fetchable from the LAN).
- Which page a site gets is decided at render time from the site's kind, as T124 already does.

## Not in scope

- **Why a particular wake failed.** D1 makes wakes rare; D5 makes a failed one visible. A specific
  failing path found later is a bug of its own.
- **The daemon at login** (T85b) — see D4.
- **Removing idle shutdown.** It stays, measured and exempting exactly as today, behind D1's switch.

## Decision record

**ADR 0041 — MixEngine stops nothing a person did not ask it to stop.** Records D1 and D4 (idle off
by default behind one home switch; the front end autostarts), superseding the *defaults* T70/T70a
chose (not their mechanism). `resource-isolation.md` is rewritten to match: section 2's table becomes
"when saving resources is on", and section 1 names the front end as always started.

## Tests

- Generator: a `NULL` row gets no idle policy with `save_resources = false`, the saving default with
  `true`; a row at `n` gets `n` either way; `0` gets none either way.
- `service.set_save_resources` writes the `settings` row, `service.save_resources` reads it back,
  and the next generated spec of a `NULL` row carries the saving policy.
- `ServiceSummary.stopped_by` for a person's stop, an idle stop, a never-started row; absent while
  running. Bindings regenerate (`packaging/bindings.sh`).
- `serviceStateLabel`: `(stopped, daemon)` → resting label and tone; `(stopped, person)` and
  `(stopped, undefined)` unchanged.
- D4: a new front end is created with `autostart = true`; the migration flips existing front-end
  rows and nothing else.
- D5: both front ends render the *starting* page for a site with a backend and the welcome page for
  one without; the page carries no path, no port, no account.
