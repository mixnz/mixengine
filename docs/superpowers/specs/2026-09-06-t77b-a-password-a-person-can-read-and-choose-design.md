# T77b — A password a person can read, and a password a person chooses (design)

Roadmap task **T77b**, phase 8, a follow-up to T77a inserted after T84. T77a made
`mix database create` and decided, in its D11, that *nothing prints the password and nothing puts it
on the wire*: the call answers the keyring address, and T83's `mix database open` is the one thing
allowed to read the entry, into the environment of a process the daemon starts. That is a complete
design for exactly one consumer — a desktop client MixEngine launches — and the first person to use
it for the ordinary reason found the hole: **a project's `.env` needs the password, and there is no
sanctioned way to get it there.** The credential exists, in Credential Manager, and the only
program that will hand it over is a program that opens a GUI.

## Goal

Two things, each a command, both leaving T77a's ownership rule and T83's handoff exactly as built.

1. **`mix database credentials <service> [--user <account>]`** prints the password MixEngine holds
   for an account, so that it can be put where a project reads it. It is the command
   `architecture/security-model.md` has promised since before T33 — *"`mix service credentials <id>`
   reveals it on demand"* — and that T82 found did not exist.
2. **`mix database create … --password [<value>]`** lets the person choose the password rather than
   have one generated, so that a `.env` written first and a database made second agree without a
   copy step. The chosen password goes into the keyring exactly where a generated one would, which is
   what keeps `mix database open` and `mix blueprint apply` unaware that anything changed.

## Measured, not assumed

Every line below was read off this workspace or off the machine this was designed on.

- **`database.create` answers `DatabaseAccount { service, database, user, secret, made }`** and
  `secret` is a `SecretAddress { service: "mixengine", key: "<service-id>/<user>" }` — the address
  and never the value (`mixengine-proto/src/database.rs`). Its module note cites T77a's D11 and ADR
  0006; two tests, `nothing_on_the_wire_is_shaped_like_a_password` and
  `a_handoff_names_the_keyring_address_and_nothing_shaped_like_a_password`, assert that the
  *serialised* `DatabaseAccount` and `DatabaseHandoff` contain no such word. Three CLI suites
  (`tests/mariadb.rs:491`, `tests/mysql.rs:453`, `tests/postgres.rs:445`) assert the same of the
  created answer.
- **The password is generated by `mixengine_platform::generate_secret(32)`** from an alphabet of
  `[A-Za-z0-9]` — `mixengine-platform/src/secrets.rs`, `SECRET_LENGTH` in
  `mixengine-core/src/generate/databases.rs`. It is written to the keyring **before** any statement
  runs (`daemon/src/services/databases.rs`, the module note's step 4), so that a failure afterwards
  leaves a credential for an account the next attempt creates with exactly it.
- **Every recipe interpolates the account's password into SQL unescaped.** `mysql_family.rs:124`:
  `IDENTIFIED BY '{password}'`; `postgres.rs:429`: `LOGIN PASSWORD ''{password}''` inside a string
  handed to `\gexec`. That is safe today for one reason, stated at `generate/databases.rs:16`
  *"Validated, never escaped"* and at `recipes/mariadb.rs:397` *"Refused rather than escaped"*: the
  only producer of the value is the generator, whose alphabet cannot end a quoted literal. A value a
  person typed has no such producer.
- **The ownership rule is a pure function**, `decide(found, stored)` in
  `daemon/src/services/databases.rs`: a stored entry means *ours* whether or not the server has the
  account, no entry and no account means *generate*, no entry and an account means *foreign* and
  the call is refused with `conflict`. `ensure` then runs statements written to be true of a server
  in either state — `CREATE USER IF NOT EXISTS … ; ALTER USER … IDENTIFIED BY …` — so the server is
  realigned to whatever the keyring holds on every call.
- **The keyring trait already replaces**: `Keyring::set_secret` is documented *"replacing whatever
  was there"* (`platform/src/traits/keyring.rs`). Nothing new is needed of the platform layer.
- **`read` and `write` exist in the daemon and nowhere else**:
  `crate::services::databases::read(host, address)` is what `database.open` already calls to read a
  credential at the moment of a handoff. A `credentials` method is that read with a response instead
  of an environment.
- **The administrator is not an account `database.create` knows about**: `database.open` and
  `database.client` get it from `handoff::address(...)`'s `administrator` (the recipe's `root` /
  `postgres`), and `database.open` defaults `user` to it. Redis and Memcached have no administrator
  and no accounts (`DatabaseProtocol::has_accounts`).
- **The one place `mix` reads its own standard input is `confirm.rs`**, whose module note fixes the
  rule this task reuses: *the decision is what can be read, not `IsTerminal`* — a line is an answer,
  end of file is `Unanswerable`, and the prompt goes to standard error.
- **No crate in the workspace hides terminal echo.** `mixengine-cli`'s dependencies are clap, hyper,
  serde, qrcode, tokio and three workspace crates. Turning echo off is a console call on each OS,
  which by `CLAUDE.md` would have to live in `mixengine-platform`.
- **The IPC endpoint is owner-only and kernel-enforced** — `architecture/daemon-and-ipc.md`: socket
  mode `0600` with peer credentials checked, or a pipe whose DACL names one SID and whose owner the
  client verifies before sending. Whoever can call `database.credentials` can already run
  `mix database open`, which puts the same password in a process's environment; and can already
  open Credential Manager, where the entry is listed under `mixengine`.
- **`architecture/security-model.md:163` names `mix service credentials <id>`**, and
  `roadmap/phase-8-differentiators.md:394` records, under T82, that *"the manifest cited a
  `mix service credentials` that does not exist"*. The document has promised the command for the
  root password since it was written; this task delivers it under `mix database`, where every
  other credential-shaped verb already lives, and corrects the sentence.
- **`docs/guide/en/cli.md` is generated** — `bash packaging/docs.sh --reference` — from the
  binary's own clap definitions; `docs/guide/{en,vi}/services.md` are written by hand and both say
  *"Nothing prints the password"* in so many words.

## Scope

**In:**

- `mixengine-proto` — `DatabaseCreate.password: Option<String>`; `DatabaseCredentialsQuery`;
  `DatabaseCredentials`, the first response type in the workspace that carries a password, with a
  hand-written `Debug` that does not; the method name `database.credentials`; regenerated bindings.
- `mixengine-core` — `validated_password`, beside `validated_identifier` and for the same reason.
- `mixengine-daemon` — `database.credentials`; `database.create` taking the caller's password
  through the existing `decide` / `account_password` path with one new branch.
- `mixengine-cli` — `mix database credentials`, `--password [<value>]` on `mix database create`,
  the second reader of standard input in the binary, the renderings.
- The documents this makes wrong, listed at the end, including the one ADR.

**Out:**

- Hiding echo while a password is typed. See D5.
- Changing the administrator's password. `credentials` reads it; nothing here writes it. Rotating
  root is a different operation with a different blast radius (every extension pool T82a resolved
  it into) and nobody has asked for it.
- `database.open` learning a `--password`. It reads the keyring, which is the point.
- Any change to what `mix blueprint apply`'s `CreateDatabase` sends. It generates, as before.
- Writing the `.env` file. MixEngine prints; the person pastes. A `.env` is the project's and every
  framework spells its keys differently.

## Decisions

### D1 — Reading a credential is its own method, and it is a read

`database.credentials` takes `{ service, user? }` and answers
`{ service, user, secret: SecretAddress, password }`. `user` defaults to the administrator, as
`database.open`'s does — the two commands are the same question with two different consumers, a
process and a person, so they take the same arguments and default the same way.

It reads and nothing else. It does not start the instance (the keyring is not on the server), it
does not probe the server, and it does not create what is missing: an account MixEngine holds no
entry for is `precondition_failed` with `database.open`'s own hint —
*"`mix database create <service> --name <database> --user <account>` makes one"* — and the
administrator's absence is the same code with the same *"written by the service's first run"* hint,
because both sentences already exist in `Databases::credential` and this method calls it. Redis
and Memcached answer `invalid_argument` *"has no accounts"*, as `open --user` does.

The method lives under `database.*` rather than `service.*`. `security-model.md` wrote
`mix service credentials <id>` before `mix database` existed; today every verb that names a keyring
entry is a `database.*` verb, the type it returns is composed of `database.*`'s types, and a
`service.credentials` that answered for MariaDB and refused for Caddy would be a method whose
argument decides whether it exists.

### D2 — The password crosses the wire once, in a response, and only when asked for by name

This overturns the sentence at the head of `mixengine-proto/src/database.rs` — *"what is not here is
the password"* — for one type, and states the narrower rule that replaces it: **a credential is in
a response only from a method whose whole purpose is to answer it, and never as a member of a
response that has another purpose.** `DatabaseAccount` and `DatabaseHandoff` stay exactly as they
are, and their tests stay green; `DatabaseCredentials` is the exception, and the test that guards
the rule is inverted for it — the serialised form *does* contain the password, because a reader
asked.

Why this is safe to write down: the transport is owner-only and kernel-enforced (measured above),
and the same owner already has the entry two other ways. ADR 0006 is untouched — a `ServiceSpec`
still names a credential and cannot carry one; that rule is about a document generated to disk and
supervised for hours, and this is a reply that exists for the lifetime of one request. What the
new rule adds is a `Debug` that redacts, the way `Credentials` in `generate/databases.rs` already
does, so a `tracing` line on a failed request cannot print it.

Recorded as **ADR 0025** — *a credential is answered only by a method that exists to answer it* —
because three tests and two documents state the old rule, and the next person to add a field
called `password` to a response should find a decision, not a precedent.

### D3 — The CLI prints the address and the password, on standard output, and `--json` carries both

```
password for blog on mariadb@main
  stored in the mixengine credentials at mariadb@main/blog
  Xk3…​(32 characters)
```

The password is the last line and nothing else is on it, so that `tail -1` is a value; `--json`
answers the response object as every other command does. There is no `--raw` and no second output
shape: a script has `--json`, and a person has the last line.

It is printed to standard output and not standard error, because it is the answer and standard
output is where answers go; that it will land in a terminal's scrollback is what the person asked
for by typing the command. `mix` does not log its own output, and the daemon logs the request's
method and never its response.

### D4 — A chosen password is validated, never escaped, and the validator is the recipe's guarantee

`validated_password` in `mixengine-core::generate::databases`, called before anything is started,
on `validated_identifier`'s reasoning: every statement interpolates the value into a quoted literal,
nothing escapes, so the characters that could end the literal are refused rather than handled.

Refused: `'` (ends both dialects' literal), `\` (MySQL's escape character; the line a `psql` script
reads begins a meta-command with it), any whitespace (a `.env` line ends at it in half the parsers
that exist), any control character, anything outside printable ASCII (the two clients' console
encodings differ per OS and an account whose password is read back as different bytes is an account
nobody can use). Length `1..=128`. Everything else printable is allowed, including `"`, `$`, `#`
and `` ` ``: they are the person's `.env` parser's problem and that person is the one typing them.
The error names the character class and never echoes the value.

No minimum beyond non-empty. A local development database on a loopback port protects nothing a
stronger password would protect, and a rule that refused `secret` would be a rule people route
around with `secret123`. The generator still produces 32 characters when nobody chooses.

### D5 — `--password` takes a value, or takes a line from standard input, and echo is not hidden

`--password [<value>]` — clap `num_args = 0..=1`. With a value, that is the password. Without one,
`mix` prints `password for <account> on <service>: ` to standard error and reads one line from
standard input, by `confirm.rs`'s rule: a line is the answer, end of file is refused with the
sentence *"nobody to ask — pass `--password <value>` or pipe one line in"*. So `echo secret | mix
database create … --password` works from a script, and typing it works from a keyboard, and
neither depends on whether standard input is a terminal.

Echo stays on. Hiding it is a per-OS console call — `SetConsoleMode`, `tcsetattr` — that would
have to be a `mixengine-platform` capability and a new trait for a value the person is about to
paste into a plaintext `.env` in the next ten seconds. The `--help` text says the value is shown
as typed, and the value form is the one every other flag in `mix` has, visible in a process list
for the milliseconds `mix` runs; the same is true of `--user` today. The daemon side keeps its
stricter rule unchanged: the password reaches the SQL client on standard input and the
administrator's through `MYSQL_PWD` / `PGPASSWORD`, never in `args`.

### D6 — A chosen password goes through `decide`, and it adds one branch rather than a bypass

`decide(found, stored)` gains a third input, `chosen: Option<String>`, and stays pure:

| server has the account | keyring holds | chosen | result |
| --- | --- | --- | --- |
| no | none | none | `Generate` — as today |
| no | none | yes | `Store(chosen)` — written before any statement, as a generated one is |
| any | some | none | `Stored(existing)` — as today |
| any | some | yes | `Store(chosen)` — the keyring is replaced, and `ALTER USER` realigns the server |
| yes | none | any | `Foreign` — refused, as today |

The last row is the whole reason this goes through `decide` and not around it: **knowing a
password is not ownership.** An account on the server that MixEngine holds no entry for is
somebody else's, and a person who types its correct password has proved they know it, not that
MixEngine should now hold it — the deed T77a's D3 issued is the keyring entry, and this task issues
it only where D3 would have. The fourth row is the one that is new in kind — a password *changes* —
and it is the row a person actually reaches for: *I made `blog` yesterday, now I want it to be
what my `.env` says.* The answer's `made.user` is `existing` in that row, as now; nothing in the
response says a password moved, because nothing in the response describes passwords (D2).

`Store` replaces `Generate`'s write with the chosen value; the ordering — keyring first, statements
second — is unchanged and for T33's reason.

### D7 — The two documents that said "nothing prints the password" say what is true instead

`features/services.md`, `docs/guide/en/services.md` and `docs/guide/vi/services.md` each say the
password is never printed. After this task that sentence is false, and the true one is: *it is
stored in the credential store and printed by nothing but `mix database credentials`, which exists
so that a project's `.env` can hold it.* `security-model.md`'s `mix service credentials <id>`
becomes `mix database credentials <id>`. The `--help` for `create` loses *"Nothing prints the
password"* and gains the two flags' sentences; `cli.md` is regenerated from it.

## Data flow

**`mix database credentials mariadb@main --user blog`**

1. `mix` sends `database.credentials { service, user: "blog" }`.
2. The daemon validates `user` as an identifier; reads `handoff::address` for the service — a
   service with no address or no accounts is `invalid_argument`; a service not declared,
   `not_found`.
3. `user` defaults to the address's administrator when absent.
4. `handoff::secret_key(service, user)` composes the key; `Databases::credential` reads it through
   `services::databases::read`, on `spawn_blocking`, and turns absence into the two
   `precondition_failed` sentences that exist.
5. `DatabaseCredentials { service, user, secret: SecretAddress::of(key), password }` goes back.
6. `mix` renders D3's three lines, or the object.

**`mix database create mariadb@main --name blog --password`**

1. `mix` sees the flag with no value, prompts on standard error, reads one line; end of file exits 1
   with D5's sentence before anything is sent.
2. `database.create { service, database: "blog", user: None, password: Some(line) }`.
3. The daemon validates the identifiers, then `validated_password` — refused before the instance is
   started, on the existing reasoning.
4. Everything as T77a from here: provisioning vocabulary, the per-instance gate, `ensure_running`,
   the probe, `decide(found, stored, chosen)` (D6), the keyring write, the statements, the last of
   which signs in as `blog` with the chosen password and creates a table.
5. `DatabaseAccount` goes back unchanged in shape.

## Testing

**`decide`, without a server.** The five-row table of D6 is a table test on a pure function, as the
three-row one is today; the row that refuses a known password for a foreign account is the one
that matters and is named as such.

**`validated_password`, without a server.** Accepts `secret`, `p@ss$word#1`, 128 characters;
refuses the empty string, `'`, `\`, a space, a tab, `é`, 129 characters. One test walks every
recipe's `steps` with a chosen password containing every accepted punctuation character and asserts
the SQL still contains the literal exactly once per statement — the property the validator exists
to keep true.

**The wire, in `mixengine-proto`.** `DatabaseCredentials` serialises with `password` present and
`Debug` prints `<n bytes>`; `DatabaseCreate` with `password: None` serialises without the member,
so a client built before this task sends what it always sent and a daemon built before it reads
what it always read (ADR 0019).

**`database.credentials` in the daemon, with the mock host.** Administrator by default; a named
account; an account with no entry answers `precondition_failed` with the `create` hint; the
administrator with no entry answers the `first run` hint; Redis answers `invalid_argument`. All of
it against `MockHost`'s keyring, which is what `databases.rs`'s existing tests already use.

**Against real servers.** In `tests/mariadb.rs`, `tests/mysql.rs` and `tests/postgres.rs`,
extending the *database and an account* group: `create --name shop --password <chosen>` succeeds —
which by T77a's D13 is the daemon signing in with that password; `credentials --user shop --json`
answers exactly the chosen value; `create --name blog --password <other>` on the account made
earlier succeeds with `existing` and `credentials --user blog` now answers `<other>`; and a
`--password` containing `'` is refused with `invalid_argument` and no server started. The suites'
existing *"the answer carries the address and never the credential"* assertions on `create` stay:
D2 leaves them true. The macOS note in those suites — reading a credential prompts — is why the
`credentials` calls go through `mix` and the daemon and never through the test process's own
keyring access.

**The prompt, in `mixengine-cli`'s own tests.** `--password` with a line on standard input sends
it; with standard input closed exits 1 with D5's sentence and sends nothing — the shape
`confirm.rs`'s tests already have.

## Risks, and where each is answered

- *A password now appears on a terminal.* Because a person typed a command whose name is
  `credentials`; D3. The alternative was the status quo, in which it appears in Credential Manager's
  own window, which is where the first user of this feature went.
- *A response carries a secret and some later `tracing` line prints it.* `Debug` redacts, D2, and
  the test says so.
- *A chosen password breaks a statement.* Validated against the literal's own terminators, D4, with
  a test that runs every recipe's SQL builder over the accepted alphabet.
- *A person types a foreign account's real password and expects MixEngine to adopt it.* D6's last
  row refuses, with the `conflict` sentence T77a already writes. The design choice is named there.
- *Old client, new daemon; new client, old daemon.* `password` is optional and absent when unset;
  `database.credentials` on an old daemon is the dispatcher's *"this daemon has no method"*
  sentence with its `daemon.version` hint, which `mix` already renders.
